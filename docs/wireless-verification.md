## 2026-10-22 추가 확인: Windows 화면 캡처 호환성

Windows의 Wi-Fi/LAN을 켰는데 iPad의 HELLO 요청에 응답하지 않거나 페어링 창이
바로 닫히는 사례에서, 전달받은 PC 로그는 캡처 초기화 오류
`E_NOINTERFACE (0x80004002)`를 반복했다. UDP 수신이 시작된 뒤 캡처가 실패하면서
전송 경로도 닫혔다. 따라서 이 사례는 네트워크 허용 설정만으로 해결할 수 없다.

해당 PC의 별도 캡처 점검 결과는 다음과 같다. 개인 기기 이름과 주소는 제외했다.

```text
Windows 10.0.22621.4317 (Windows 11 22H2)
WGC supported: true
Empty frame pool: handled without a capture error
Monitor: 1920 x 1080
Session-local exclusion: UNAVAILABLE (0x80004002)
Exit code: 1
```

WGC(Windows 화면 캡처) 자체가 지원돼도, DeskInk가 필기의 중복 캡처를 막는 데
사용하는 세션별 창 제외 인터페이스가 없으면 초기화에 실패한다.
현재 USB와 LAN은 이 캡처 경로를 함께 사용한다. 단순히 CPU 제조사가 다르거나
무선 연결이라서 생기는 오류라고 분류해서는 안 된다.

개발 PC의 Windows 11 25H2 빌드 `26200.9711`에서는 같은 인터페이스 확인이
성공했다. 이 두 관찰만으로 모든 Windows 11 또는 모든 25H2 설치의 호환성을
보장하거나, 정확한 최소 누적 업데이트 번호를 확정할 수는 없다.
문제가 있는 PC에는 Windows 업데이트에서 제공하는 기능·누적 업데이트를 적용한
뒤 다시 점검하도록 안내한다. 전달받은 PC가 업데이트 후 해결됐다는 실기기
재검증 기록은 아직 없다. 이번 안내서 수정에는 캡처 우회나 앱 바이너리 변경이 없다.

근거: [Microsoft Windows 11 버전 정보](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information),
[세션별 창 제외 API](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.idisplaygraphicscapturesession.setwindowexclusionlist?view=winrt-28000),
[캡처 샘플 유지보수자의 인터페이스 지원 설명](https://github.com/robmikh/Win32CaptureSample/issues/106).
이는 이전에 보고된 무선 필기 가림 현상의 원인을 확정하는 결과는 아니다.

## 구현과 검사 경계

Windows에서 `Wi-Fi / LAN`을 펼쳐 `Allow Wi-Fi / LAN`을 켰을 때만 네트워크로
접속할 수 있다. 기본은 꺼짐이며 USB는 기존 설정으로 사용한다. iPad는 주소만
담긴 QR 또는 직접 IP 입력, Android는 직접 IP 입력으로 PC를 선택한다. 처음
등록할 때는 기존 6자리 코드가 별도로 필요하다. Wi-Fi에는 Windows와 태블릿 앱
모두 0.5.0이 필요하고, 이전 태블릿 앱의 USB 연결은 유지한다.

영상은 기존 UDP 전송·패킷 간격 조절·혼잡 피드백 경로를 사용한다. 필기는 별도의
확인 응답 채널을 사용하며, 정상 순서의 입력은 기다리지 않고 바로 적용한다.
손실·중복·순서 뒤바뀜을 복구하되 대기량과 입력 나이를 제한한다. USB 영상 압축,
필기 프레이밍, 재전송 없는 USB 경로를 무선 동작으로 바꾸지 않는다.

필기 검사의 경계는 실제 입력 메시지 → 인증·순서 판정 → 보드 변경·확인 응답이다.
전송 검사는 실제 UDP 소켓과 `start_sender`를 통과해 페어링, 영상 페이로드,
현재 연결의 필기를 확인한다. 이것은 무선 공유기·태블릿 하드웨어·Zoom이 포함된
실제 펜 지연 측정과 별개다.

프로토콜 제한은 다음과 같다.

- `HELLO2` 필기 기능 비트는 `FEATURE_RELIABLE_INK = 0x0010`, 호스트 기능 비트는
  `0x8000`이다. 필요한 기능을 지원하지 않는 네트워크 클라이언트는 허용하지 않는다.
- 무선 필기는 `DI02` + 기존 버전 1 JSON이며 JSON은 최대 1,024바이트다.
  USB는 기존 `DI01`을 유지한다.
- `DA02` 확인 응답은 정확히 20바이트이며 세션, 스트림 세대, 연속 적용한 마지막
  순번을 담는다. 현재 peer·session·epoch에 해당하는 입력만 적용한다.
- 대기·재정렬 창은 최대 256개다. 첫 전송은 즉시 하고 누락된 입력은 약 20ms
  간격으로 다시 시도한다. 가장 오래된 미확인 입력이 250ms에 도달하면 연결을
  끝내며, 오래된 필기를 몇 초 뒤 한꺼번에 재생하지 않는다.

## 테스트를 먼저 추가한 기록

- `wireless-host-red.log`: `AnnotationState::receive_lan`이 없는 상태에서 새 입력
  경계 검사가 컴파일 실패했다. 구현 후 동일 검사와 USB 세션 6개가 통과했고,
  이후 인증·크기·입력 나이 제한을 포함한 무선 필기 3개로 확장했다.
- `wireless-transport-red.log`: `SharedControl::lan_enabled`가 없는 상태에서
  네트워크 기본 비활성화·실제 UDP 통합 검사가 컴파일 실패했다. 구현 후
  `wireless-transport-green.log`의 20개 통합 검사가 통과했다.
- `wireless-frame-sequence-red.log`: 실제 UDP 전송 검사에서 LAN 프레임 순번의
  기대값 `1` 대신 캡처 순번 `7`을 받아 실패했다. 컴파일은 6분 38초 걸렸고
  검사는 실행 후 0.56초에 실패했다. LAN에 별도 연속 순번을 부여하는 수정 후
  `wireless-frame-sequence-final.log`에서 동일 실제 UDP 검사가 1개 통과했다.
  `wireless-frame-sequence-green.log`는 transport 라이브러리 54개가 통과했지만
  통합 검사 1개는 필터로 제외되어 있었으므로, 그 실행만으로 회귀 검사 통과를
  주장하지 않고 별도 필터 없는 최종 실행을 확인했다.
- iPad 입력 대기열은 큐 진입 전 개수·입력 시각을 제한하고 공개 경계 검사를
  추가했다. 코드 후속 검토와 입력 큐 진입 검사 8개를 포함한 최종 190개 검사가
  통과했다. USB는 기존 프레이밍 경로를 유지한다.

첫 두 항목은 새 공개 경계가 존재하지 않아 실패한 기록이다. 이미 존재하던 기능의
실행 중 오류를 재현한 것처럼 해석하지 않는다.

## Standards

독립 검토에서 다음 2개 항목을 보고했다. 저장소 지침과 별개로 적용한 코드 냄새
기준은 판단을 돕는 기준이며, 자동으로 강제 위반으로 간주하지 않는다.

1. **P2, 코드 수정·후속 검토 완료:** iPad `ControlChannel.swift`의 `queue.async`가 무선 필기를
   무제한으로 먼저 쌓을 수 있고, `ReliableInkSender.swift`의 입력 나이는 그
   작업이 실행된 뒤 시작한다. 송신 창의 256개·250ms 제한만으로는 앞단 대기를
   제한하지 못하던 문제였다. 무선 입력을 큐에 넣기 전부터 개수와 최초 입력
   시각을 추적하고, 그 시각을 송신 창까지 전달한다. 후속 검토에서 수정됨을
   확인했고 공개 경계 회귀 검사를 포함한 최종 CI도 통과했다.
2. **낮은 우선순위 권고, 유지:** Android `MainActivity`에서 USB/LAN에 따른
   종료·키프레임 요청·필기 바인딩·클라이언트 생성 분기가 반복된다. 공통
   인터페이스가 분기를 줄일 수 있으나, 동작이 좋은 USB 경로를 보존하는 이번
   범위에서는 광범위한 추상화 변경을 미룬다.

검토에서 다른 인증·세션·스트림 세대·모니터·기본 비활성화·USB 보존 문제는
추가로 보고하지 않았다. 후속 검토에서도 새 문제를 보고하지 않았다.

Standards: 총 2개 중 가장 높은 P2는 코드 수정·후속 검토·관련 검사 완료, 낮은 우선순위 권고 1개는 유지한다.

## Spec

같은 기준점에서 요구사항 충족 여부를 별도로 검토하여 다음 2개 항목을 보고했다.

1. **P1, 코드 수정·후속 검토 완료:** Android `UdpFrameAssembler`는 영상 순번이 직전 값 + 1일
   것을 요구하지만 Windows는 캡처 단계의 순번을 그대로 보낸다. 캡처를 건너뛰어
   정상 영상이 10 → 12로 전송되면 클라이언트가 손실로 판단해 약 50ms 뒤
   폐기·키프레임 요청을 반복할 수 있던 문제였다. LAN 전송 영상에 연속된 순번을
   붙이고 USB 번호 동작은 유지하도록 수정했다. 실제 UDP 회귀 검사는 수정 전
   실패와 수정 후 통과를 확인했다.
2. **P2, 코드 수정·후속 검토 완료:** iPad의 무제한 앞단 입력 큐와 늦게 시작하는 나이 측정이
   “대기를 제한하고 오래된 필기를 재생하지 않는다”는 요구사항을 충족하지 못한다.
   큐 진입 전부터 제한하도록 수정했다. 같은 결함을 Standards에서도
   발견했으나 두 검토의 결과는 독립적으로 기록한다.

다른 인증·세션·스트림 세대·모니터·기본 비활성화·USB 보존 문제나 요구하지 않은
기능 확대는 추가로 보고하지 않았다. 두 검토자는 후속 코드에서 P1·P2 수정과
추가 문제 없음을 확인했다. 이 검토 통과를 최종 자동 검사나 실기기 확인의
통과로 대신하지 않는다.

## 실제 기기 확인 목록

아래는 자동 검사로 대체할 수 없는 항목이며 **아직 실기기 확인하지 않았다.**
모델·OS·PC/GPU·공유기·접속 방식·영상 설정과 함께 결과를 기록한다.

1. 기존 USB 연결로 현재 동작을 확인한다. 같은 PC·태블릿·해상도·FPS 설정으로
   비교하고, Windows 0.5.0에서 이전 태블릿 앱의 USB 연결도 확인한다.
2. Windows와 태블릿을 0.5.0으로 업데이트한다. USB를 빼고 연결을 종료한 뒤
   Windows의 `Wi-Fi / LAN`을 펼쳐 접근을 켠다. PC 이더넷 + 태블릿 Wi-Fi와
   양쪽 Wi-Fi를 각각 확인한다. 신뢰하는 같은 로컬 네트워크에서만 검사한다.
3. iPad QR과 직접 IP, Android 직접 IP를 각각 사용한다. 처음 등록은 6자리 코드,
   등록한 PC의 재접속은 기존 등록으로 연결되는지 확인한다. iPad 로컬 네트워크
   권한 거부·허용, 잘못된 IP·포트·코드에 대해 안내가 맞는지 확인한다.
4. PC 두 대를 한 번에 한 대씩 전환하고 Screen 1 → 2 → 1을 오간다. 두 PC의 등록과
   각 화면의 필기가 섞이지 않는지, 이전 연결의 늦은 입력이 새 화면에 적용되지
   않는지 확인한다.
5. 펜·형광펜·지우개·레이저·사라지는 펜·실행 취소·다시 실행·전체 지우기를 양쪽
   화면에서 확인한다. Apple Pencil 두 번 탭, S펜 버튼을 누르는 동안 지우개 및
   놓았을 때 이전 도구 복귀, 손바닥과 두 손가락 확대·이동을 확인한다.
6. 잠자기·깨어나기, 앱 닫기·다시 열기, 짧은 Wi-Fi 끊김과 재접속, PC 주소 변경을
   확인한다. 오래된 필기가 뒤늦게 몰아서 나타나지 않아야 한다. 네트워크 접근을
   끈 뒤 USB로 돌아가 기존 동작을 다시 확인한다.
7. 지연을 비교할 때는 같은 필기 동작을 고속 카메라로 촬영해 펜 접촉→태블릿 화면,
   펜 접촉→Windows 화면을 구분한다. 평균뿐 아니라 느린 구간과 끊김을 기록한다.
   영상 디코더 FPS를 펜 전체 지연으로 간주하지 않는다. 아직 측정값이나 지연 0을
   보장하는 결과는 없다.
8. 30~60분 연속 사용하며 양쪽 필기·영상 반응이 누적해서 느려지는지 확인한다.
   Zoom에서는 필기할 모니터 전체를 직접 공유하고 다른 참가자 화면에서 필기·
   포인터를 확인한다. Zoom 전송 지연은 DeskInk 로컬 지연과 별도로 기록한다.

Windows 방화벽은 배포 폴더의 `bin/deskink.exe`, 표시된 UDP 포트(기본 9876),
개인 네트워크·로컬 서브넷으로 제한한다. 방화벽 전체를 끄거나 공유기 포트 포워딩을
설정하지 않는다. 화면과 필기 트래픽은 암호화되지 않으며, 게스트 Wi-Fi·기기 간
통신 차단·기관의 네트워크 정책은 연결 가능 여부와 실측 지연에 영향을 준다.

기준점 `8d2deb3` 이후 Windows 인앱 업데이트와 USB 우선 자동 연결 변경을 검토했다.
최종 코드에서 추가 배포 차단 결함은 찾지 못했다. 이 기록은 아래 자동 검사와 코드
검토의 범위이며, 0.5.1 공개 배포 완료나 실기기 검증 완료를 뜻하지 않는다.

- **설치 CLI 12개 통과:** 실제 PowerShell `Stage`/`Apply` 입구를 임시 포터블 폴더와
  시험용 패키지로 검사했다. 설치 폴더·런타임·사용자 파일 보존, 다운로드 중 변경된
  파일 보존, 체크섬·파일 manifest·ZIP 경로 검증, 외부 다운로드 주소·이전 버전 거부,

  강제 종료하지 않는 대기, 종료 전 준비 신호를 포함한다. 전체 실행 20.6초였고,
  준비 신호를 실패 시 무효화한 뒤 관련 2개도 다시 통과했다.
- **업데이트 명세 검사 2개 통과:** 같은 버전·같은 소스의 문서 변경에는 재설치를

  이전 버전으로 되돌리는 제안을 막는다.
- **LAN 공개 전송 접점 회귀 검사 1개 통과:** 기존 실제 UDP 연결·인증·영상·필기
  동작을 다시 확인했다. 실제 태블릿이나 공유기의 지연 측정은 아니다.

검토 중 설치 도우미가 기존 설치 폴더를 작업 디렉터리로 상속받아 폴더 이동에 실패하는
문제를 공개 CLI 검사로 재현했다. 도우미의 프로세스 작업 디렉터리와 PowerShell 위치를
별도 작업 폴더로 옮겨 해결했고 재검사를 통과했다. 폴더 잠금 후 재시도할 때 이전
사용자 파일 복사본을 복원하던 문제도 실패 검사 후 수정했다.

업데이트 확인·다운로드·검증은 필기와 영상 스레드 밖에서 실행한다. 다운로드만으로
앱을 닫지 않으며, 사용자가 `Install and restart (clears ink)`를 누르고 검증된 도우미가
준비 신호를 보낸 뒤에만 종료한다. 시간이 지난 준비 신호나 종료된 도우미는 앱을
닫게 하지 않는다. 현재 필기가 지워짐을 버튼 옆에 표시한다. 설정과 페어링 저장소는
설치 폴더 밖에 유지한다. 업데이트 UI는 기존 세로 스크롤 영역 안에 있다.

새 호스트의 실행 확인은 **프로세스가 2.5초 동안 종료되지 않았는지** 확인하는 절차다.
GPU 초기화·실제 화면 수신·펜 입력 건강 상태를 보장하지 않는다. 설치 CLI 검사는
시험용 패키지를 사용하며 실제 GitHub 다운로드 전체 경로나 사용 중인 DeskInk의
업데이트를 대신 검증하지 않는다. SHA-256 검증을 코드 서명 인증으로 표현하지 않는다.
전원 차단이 두 폴더 이동 사이에 발생하는 경우까지 원자성을 보장하지 않으며, 복원에
실패하면 백업 경로를 남긴다. USB↔Wi-Fi 실기기 전환·장시간 사용·Zoom 지연 측정은
기존 실기기 확인 목록에 남는다.

## 0.5.1 태블릿 연결·패키지 후속 검증

- iPad 자동 연결은 실제 UDP 호스트와 USB TCP 터널, H.264 수신·디코딩,
  필기 화면 입력을 거치는 통합 검사 10개를 추가했다. 저장된 LAN으로 시작,
  USB 우선권·제거 후 같은 PC 복귀, 다른 PC 자동 선택 방지, X 이후 일시 중지,
  무선 필기 전송, 버전 오류 설명 유지와 재시도 중지를 확인한다.
- 저장된 LAN으로 시작하지 않는 실패와, 응답하지 않는 다른 PC를 수동 선택한 뒤
  백그라운드에서 복귀하면 이전 PC로 넘어가는 실패를 각각 먼저 재현하고 수정했다.
  자동 복귀는 현재 선택한 주소·포트와 인증된 PC 식별자를 확인한다. 인증 토큰은
  기존 Keychain 저장소를 사용하고 UserDefaults에 복사하지 않는다.
- iPad 전체 재검사 `39556006964`에서 200개 테스트가 통과했다. 직전 실행에서는
  기존 USB malformed-preamble 검사에서 임시 포트의 listener 준비가 한 차례
  지연/실패했다. 원래 검사가 실패 상태를 기록하지 않아 정확한 원인은 확정하지
  못했다. 실패 이유를 기록하고 포트 0으로 이어지는 부수 실패를 막은 뒤 재검사했다.
  USB 제품 코드를 바꾸거나 시간 제한을 늘려 해결했다고 주장하지 않는다.
- Android에서 연결 해제·앱 복귀 검사는 실제 lifecycle을 통해 실행한다. 새 테스트가
  `restart()`를 생략하여 두 번째 `onStop()`이 실행되지 않고 다음 테스트의 포트를
  점유하는 문제를 로컬 Robolectric에서도 재현했다. 실제 Android 순서로 수정한 뒤
  core 48개와 앱 12개가 모두 통과했다. 원래 포트 재사용 assertion은 유지했다.
- 별도로 USB preamble을 아직 보내지 않은 연결이 종료 때 남는 것을 실제 소켓으로
  재현했다. accept 직후부터 초기 소켓을 소유하고 종료 시 닫도록 수정했으며,
  EOF 또는 connection reset은 종료로, timeout은 실패로 검사한다.
- Windows Release 빌드와 `cargo check`를 통과했다. 깨끗한 소스 `90ca58d`에서
  만든 ZIP의 566개 manifest 파일 해시, 허용 목록, 실제 실행 파일과 내장 HTML을
  확인했다. 개발 도구 경로를 제거한 공백 포함 새 폴더에서 `-CheckOnly`로 런타임
  다운로드·검사·실행을 통과했다. 기존 설치 폴더를 대상으로 비파괴 Stage도 통과했다.
- HTML은 Apple/Galaxy 분리, Apple 기기 등록 우선 순서, 키보드 탭·직접 링크·이미지
  확대·인쇄·오프라인을 320·390·820·1440px에서 확인했다. 새 버전 오류·업데이트
  도움말 직접 링크도 열리고 가로 넘침이 없음을 확인했다.

자동 검사 결과와 실제 iPad/Galaxy Tab에서의 USB↔Wi-Fi 전환, Apple Pencil·S펜
지연, 30~60분 연속 사용과 Zoom 수신 결과는 구분한다. 실기기 성능은 아직 미측정이다.

### 실제 Windows 설치와 배포 파일

- 기존 바탕화면 설치에 0.5.1의 Stage/Apply를 실행했고, 새 설치의 관리 대상 566개
  파일이 패키지와 일치했다. 페어링 저장소와 LAN 설정의 해시는 설치 전후 동일했다.

  무인증 HELLO 요청에는 정상적인 페어링 필요 응답이 왔다. 태블릿 영상 수신을
  대신하는 검사는 아니다.
- 같은 실행 중인 PC에 reliable-ink 기능 비트만 달리한 무인증 LAN HELLO를 보냈다.
  이전 기능 조합 `0x09`에는 호환 불가(status 2), 현재 조합 `0x19`에는 페어링 필요
  (status 4)가 돌아왔다. 버전 오류가 연결 기능 불일치에서도 발생함을 실제 전송
  경로에서 확인했으며, 인증 정보나 페어링 코드를 전송하지 않았다.

  `Auto`/`자동`으로 줄여 수정했다. 화면 검사는 연결·자동·연결 끊기 버튼 각각의
  전체 너비·높이와 창 안쪽 경계를 확인한다. core 48개·앱 12개·일반 에뮬레이터

  보였다. APK는 기존 인증서로 서명한 버전 0.5.1(5), 최소 Android 8(API 26)이다.
- 원격 작업 중 GUI 관찰 도구에서는 필기층 창만 열거되어 업데이트 패널의 실제
  표시 상태를 검증하지 못했다. 정상 실행·백그라운드 실행과 임시 DX12 선택을
  비교해도 관찰 결과가 같았다. 공개 모니터 전환 명령은 정상 종료했으므로 이
  관찰만으로 GPU 초기화 실패라고 판단하지 않으며, 렌더러 변경도 하지 않았다.

### 2026-10-21 사용자 확인 및 필기 가림 진단

- 사용자가 Tailscale 없이 실제 iPad 무선 화면 연결 성공을 확인했다. USB 우선 전환과
  장시간 지연 측정까지 완료했다고 확대 해석하지 않는다.
- 이후 다른 창이 Windows 필기를 가리지만 iPad 필기는 위에 보이는 사진이 전달됐고,
  사용자는 USB는 정상이며 무선에서만 발생한다고 설명했다. 원인은 아직 미확정이다.
- 실제 `AnnotationSurface`와 USB/LAN 공개 입력 함수를 거쳐, 기존 일반 창을 앞으로
  가져온 경우와 새 일반 창을 연 경우에 지정된 빨간 픽셀이 모두 PC 화면 위에 남는
  것을 확인했다. 사용자 전경 창은 바뀌지 않았다. 무선 패킷 손실·재연결이나 사용자
  PC의 특정 창 상태를 재현한 검사는 아니다.
- 별도 native 검사에서는 다른 최상위 창이 올라오면 필기층이 뒤에 남는 것을 두 번
  재현했다. 하지만 USB/LAN 공통 경로이므로 무선 전용 증상의 원인으로 채택하거나
  제품의 창 순서 처리를 임의로 바꾸지 않았다.
- iPad는 로컬 문서에 선을 먼저 그린 뒤 전송한다. PC의 가리는 창을 옮겼을 때 기존
  선이 나타나는지 확인하면, 창 순서와 무선 필기 누락을 구분할 수 있다. 사용자는
  아직 이 동작을 확인하지 못했다고 답했다. 진단용 코드는 로컬 artifacts에 보관했다.

### 2026-10-23 Android 최초 무선 페어링 조사

사용자는 같은 환경에서 iPad는 연결되지만 Galaxy Tab은 IP를 직접 입력해도
연결되지 않으며, USB 없이 처음부터 무선을 사용하려고 한다고 설명했다.
실제 Galaxy Tab의 오류 문구와 코드 입력 창 표시 여부는 아직 확보하지 못했다.
아래 자동 검사에서는 해당 실패가 재현되지 않았다. **원인 확정이나 수정 완료를
의미하지 않으며, 이 조사로 제품 코드·APK·배포 파일을 변경하지 않았다.**

- `AutoConnectSessionTest.manualAddressBecomesAutomaticOnlyAfterSuccessfulPairingAndDurableSave`:
  저장된 PC가 없는 상태에서 코드 요청을 받고, 사용자가 코드를 읽는 동안 2.5초
  기다린 뒤 입력해도 연결·저장이 정상 동작했다.
- `WirelessPairingUiTest`: 실제 `MainActivity`를 Robolectric API 35에서 실행했다.
  Wi-Fi 버튼 → IP/포트 입력 → 실제 UDP 요청 → 미등록 응답 → 6자리 코드 창 →
  코드 전송 → 연결 후 도구막대의 전체 지우기 전송을 확인했다. 이 UI 검사의
  PC 응답은 공유 프로토콜 벡터를 사용하므로 실제 Windows 서버 검증과 구분한다.
- 기존 Windows `lan_transport` 검사: LAN 허용 설정, 최초 인증, 영상 패킷과
  필기 응답을 실제 `start_sender` 경로로 확인했다. 1개 통과, 0.53초.
- `WindowsLanInteropTest`: 새 Android `AutoConnectSession`과 실제 Windows Rust
  `start_sender`를 직접 연결했다. 빈 등록 목록·USB 연결 이력 없음 → 코드 요청 →
  코드 입력 → 연결 성공 → 1280×720 H.264 샘플의 UDP 재조립 → 인증된 전체 지우기
  명령이 Windows 문서에 반영됨 → 필기 ACK 이후 연결 유지를 확인했다.
  최종 재현 스크립트 실행에서 JUnit 1개 통과, 테스트 0.862초였다.

마지막 검사를 다시 실행하는 명령:

```powershell
./scripts/test-android-windows-lan.ps1
# Windows 진단 실행 파일을 이미 빌드했다면:
./scripts/test-android-windows-lan.ps1 -SkipHostBuild
```

스크립트는 Windows 빌드 의존성, JDK 17 이상과 기존 Gradle 캐시의 JUnit 4.13.2,
Hamcrest 1.3, JSON 20240303을 사용한다. Android 코어 소스 전체와 검사 클래스를
매번 직접 컴파일한다. 이번 Windows 환경에서 Gradle의 파일 감시 초기화·캐시
잠금이 검사를 막아 JVM 직접 실행으로 분리했으며, 이를 앱 오류로 판정하지 않았다.
실행별 로그는 무시 대상인 `artifacts/local/android-windows-lan/<실행 ID>/`에 남는다.

Windows 진단 실행 파일은 메모리 안의 임시 페어링, 알려진 영상 샘플과 필기 문서를
사용한다. 실제 캡처·GPU·연결된 USB 기기·사용자 설정을 사용하지 않고, 45초 후
자동 종료된다. 테스트 종료 시에도 자신이 시작한 프로세스만 정리한다.

이 검사는 PC 내부 루프백 통신이며 Galaxy 하드웨어, Android 네트워크 정책,
공유기·방화벽·다른 태블릿의 동시 연결, 실제 영상 디코딩·지연을 검증하지 않는다.
다음 단계에는 문제가 생기는 Galaxy Tab에서 다른 태블릿 연결을 끊은 상태의
재시도 결과, 6자리 코드 창 표시 여부와 정확한 오류 문구 또는 화면이 필요하다.
