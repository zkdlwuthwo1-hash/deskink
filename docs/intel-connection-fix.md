# Windows 0.4.4 — Intel PC의 페어링 직후 연결 종료

사용자가 제공한 2026-10-20 로그에서 USB 터널, 페어링, 세션 생성은 성공했다.
그 뒤 Intel UHD Graphics 730의 `h264_qsv` 초기화가 실패했고,
대체 압축기인 `libx264`도 배포 런타임에 없어 영상 전송이 종료됐다.
iPad는 이 종료를 `Connection lost — USB disconnected`로 표시했다.
이 사례의 로그는 케이블 변경이나 iPad 재설치보다 Windows 인코더 수정을 가리킨다.
원본 로그와 개인 기기명·주소·세션 번호는 저장소에 포함하지 않는다.

## 원인과 변경

- 배포 FFmpeg가 광고하는 QSV 입력은 `NV12`, `QSV`다. 기존 기본값은
  지원하지 않는 `YUV420P`였다. YUV 4:2:0 입력 모드는 이제 압축기가 받는
  메모리 배치를 고른다. BGRA 캡처를 그 형식으로 변환한다.
- `EncoderInput::pixel_format(codec)`이 실제 라이브러리 기능 조회와 선택 규칙을
  함께 담당한다. 제품 코드와 회귀 검사가 같은 공개 접점을 사용한다.
- 하드웨어 초기화 실패 시, 현재 런타임에 있는 소프트웨어 압축기만 차례로
  시도한다. Windows LGPL 구성에서는 이미 포함된 `libopenh264`로
  소프트웨어 압축한다. 별도 코덱 DLL이나 GPL 런타임을 추가하지 않는다.
- 대체 경로에서도 다음 해상도·비트레이트 변경에 사용할 입력 모드를 유지한다.
  실제로 열린 압축기 이름을 표시한다.
- QSV에는 요청한 I 프레임을 IDR로 내보내도록 설정하고 비동기 깊이를 1로
  제한했다. 지연 수치를 측정했다는 뜻은 아니다.
- NVENC·AMF의 기본 YUV420P 입력과 지원되는 직접 BGRA 경로는 유지한다.

설정 근거: [FFmpeg 7.1 QSV H.264 구현](https://ffmpeg.org/doxygen/7.1/qsvenc__h264_8c_source.html),
[FFmpeg 7.1.5 OpenH264 구현](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/libopenh264enc.c).

## 검증 범위

`scripts/test-windows.ps1`은 test-only GPL DLL을 선택하기 **전에** 배포와 같은
고정 LGPL 런타임으로 아래 검사를 실행한다. 이전에는 x264를 포함하는 개발용
런타임에서만 영상 검사를 하면 대체 경로의 결함을 놓칠 수 있었다.

| 검사 | 관찰하는 결과 | 수정 전 실패 |
| --- | --- | --- |
| 실제 QSV의 광고 형식과 선택 결과 | 기본·자동 모드의 선택값이 지원 목록에 있음 | YUV420P가 NV12/QSV 목록에 없음 |
| `run_encode_stage`에 실제 BGRA 프레임 공급 | NV12 변환 후 H.264를 엄격한 디코더로 복원하여 크기·색상 확인 | MF 설정 오류 후 없는 libx264로 종료 |
| QSV를 사용할 수 없는 PC에서 같은 영상 경로 | 실제 OpenH264로 전환하여 복원 가능한 영상 출력 | `libx264 codec not found in FFmpeg` |
| 스트림 중 키프레임 요청 | 실제 영상 출력을 확인한 뒤 요청하고 SPS/PPS/IDR부터 새 디코더로 복원 | 새 경로에 추가한 재접속 회귀 검사 |

NV12 변환 검사는 GPU 없이 실행할 수 있는 Media Foundation 코덱을 사용한다.
이 코덱을 배포 기본 대체 경로로 선택하지는 않는다. 재접속 검사는 QSV 또는
OpenH264 경로에서 수행한다. 초기화 중 버려지는 캡처 번호나 지연 출력에 붙은
캡처 번호를 실제 코덱 프레임 순서로 오해하지 않도록, 출력 수신 후 요청하고
수신한 패킷 순서로 검사한다. 이는 실제 USB·iPad 표시 지연 측정과 별개다.

로컬 PC는 AMD Radeon 740M이며 Intel 하드웨어는 없다. QSV의 **지원 형식 계약**과
**초기화 실패 후 대체 경로**를 검사할 수 있지만, Intel 하드웨어 압축 성공이나
친구의 Lightning iPad 실제 표시를 검사한 것은 아니다.
실행 중 해상도 변경과 장시간 지연을 이 테스트로 검증했다고 주장하지 않는다.

최종 실행 결과와 배포 상태는 작업 티켓
[`10-intel-video-startup.md`](../.scratch/desk-ink/issues/10-intel-video-startup.md)에 기록한다.
친구 PC에서는 Windows 앱만 0.4.4로 업데이트하고 iPad 0.4.2로 다시 연결해
실제 화면과 필기 동작을 확인해야 한다.

## 실행 결과

- 배포 인코더 형식 검사 2개, 실제 영상·재접속 검사 2개와 기존 코어·프로토콜·
  필기 세션·USB·등록 유지 검사를 합쳐 **95개 통과**.
- 공개 영상 처리 경로의 두 검사는 초기화 시점 의존을 제거한 뒤 추가로
  3회 반복하여 모두 통과했다.
- `accepted_ink_reaches_desktop_without_a_controller_ui_pass`는 현재 데스크톱에서
  실제 빨간 픽셀을 읽지 못해 실패했다. 보관된 수정 전 Release 테스트 바이너리와
  수정 후 Debug 바이너리를 같은 환경에서 실행해 동일 실패를 확인했다.
  이 테스트의 코드는 이번 수정에서 바꾸지 않았다. 원인을 인코더 회귀로
  단정하거나 기본 검사 전체가 통과했다고 기록하지 않는다.
- 별도 사용자 조작·화면 표시가 필요한 기존 진단 3개는 실행하지 않았다.
- HTML은 1440·820·390·320px에서 탭·키보드·오프라인 자산·이미지 확대·
  잘못된 이미지 복구·가로 넘침을 확인했다. Lightning 바로가기와 연결 종료
  설명을 별도로 확인하고 데스크톱·모바일 캡처를 시각적으로 검토했다.
- 메모리 한도 때문에 초기 병렬 빌드가 실패하여 이후 컴파일은 한 작업씩 실행했다.
  현재 사용 중인 앱 파일의 잠금 때문에 배포 빌드는 별도 대상 폴더를 사용한다.

## Standards

공개 접점 바깥에서 검사하던 새 형식 테스트와 중복 코덱 표시명 분기가 지적됐다.
`EncoderInput::pixel_format`에 실제 라이브러리 조회·선택을 모으고 제품·테스트의
공통 접점으로 사용했다. 표시명도 한 함수로 통합했다. 후속 검토의 미해결 항목은 없다.

## Spec

소프트웨어 경고에 `libx264` 이름이 고정되어 있던 표시 불일치를 지적받아
일반적인 소프트웨어 압축 안내로 수정했다. 인코더 선택·변환·재접속의 추가
구현 결함이나 범위 초과는 발견하지 못했다. 배포 ZIP 검증과 Intel·Lightning
실기기 확인은 코드 검토의 통과 여부와 별개로 기록한다.

## 배포 패키지 검사

Windows 0.4.4는 소스 `c5b3547d00459d8e037cdac7dc2f4c5591adcf84`에서 빌드했다.
ZIP의 SHA-256은 `547339460591f6a3cf28a9d6fa8ae8a5a3567503743a6c416963042543840288`이다.
포함 파일 565개의 검증값, 빌드한 실행 파일과의 바이트 일치, 안내서 일치,
허용 목록 및 ZIP 무결성을 확인했다. 공백이 포함된 별도 경로에 압축을 풀고
개발 도구 경로를 제거한 환경에서 첫 구성요소 다운로드·검증·실행 파일 로드가
통과했다. 실제 받은 영상 DLL도 자동 검사에서 사용한 SDK와 바이트가 같다.
현재 실행 중인 사용자 DeskInk 프로세스는 교체하지 않았다.
