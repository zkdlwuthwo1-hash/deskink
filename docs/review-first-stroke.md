# 첫 연결 구현 검토

기준: `b78d87b0783ec99122a70d79ee362254549597ef` → 첫 구현 `9da5c63`. 검토 명령은 `git diff b78d87b0783ec99122a70d79ee362254549597ef...HEAD`. `code-review` 스킬에 따라 Standards와 Spec을 서로 독립된 에이전트가 검토했고, 수정 후 각 에이전트가 해당 변경을 다시 읽었다. 전체 앱 완료 검토가 아니라 작업 01의 구현 경로에 대한 검토다.

## Standards

- 문서에 명시된 확정 규칙 위반은 발견하지 못했다. Windows 검증과 iPad 미검증도 구분되어 있다.
- 실제 결함: Windows 필기 갱신이 `App::ui()` 안에 있어 상태창 최소화 시 멈춤. `App::logic()`으로 옮겼다. 실제 입력 수신 → UI 없이 logic 실행 → 데스크톱 픽셀 검사를 추가해 실패 후 통과했다.
- 개선 판단: Swift 명령이 문자열 종류와 여러 optional 필드로 잘못된 조합을 허용함. 필요한 값을 각 case가 갖는 enum으로 바꿨다.
- 개선 판단: iPad 로컬 선과 전송할 선의 색·굵기 중복. 하나의 브러시 값을 같이 사용하도록 바꿨다.

재검토에서 위 3건의 코드상 해소를 확인했고 새로운 실제 결함은 발견하지 못했다. Swift 컴파일은 미실시다.

## Spec

- 실제 결함: 상태창 최소화 시 필기가 갱신되지 않아 작업 01의 Windows 표시 요구를 어김. `App::logic()` 이동과 픽셀 회귀 테스트로 수정했다.
- 실제 결함: 전송 간격 전에 받은 마지막 화면을 저장해도 새 캡처 알림이 없으면 500ms keepalive까지 전송하지 않음. 미전송 상태를 유지하고 다음 전송 시점까지 대기하도록 바꿨다.
- 이미 미완료로 기록한 확대·도구·저장·실기기 확인은 첫 연결 코드의 새 결함으로 중복 집계하지 않았다.

재검토에서 두 조건의 코드상 해소를 확인했다. 새 화면 처리와 버퍼 배출은 네이티브 캡처 픽셀 시험도 통과했다. 마지막 정지 화면의 지연 수치와 실제 iPad/USB/Zoom은 별도 측정이 필요하다.

집계: Standards는 실제 결함 1건·개선 판단 2건, Spec은 실제 결함 2건. 각 축의 가장 큰 문제는 최소화 시 필기 중단이었으며 수정했다. 발견하지 못했다는 것이 전체 품질이나 보안의 보증은 아니다.

## 재현과 추가 검증

- 최소화 회귀 재현 명령: `cargo test -p eternal-host --bin deskink accepted_ink_reaches_desktop_without_a_controller_ui_pass`. 수정 전 이전 색 `5883153`이 남아 실패, 수정 후 새 색 `3478509`로 통과. 실제 최소화 버튼 조작 대신 eframe이 최소화 시 사용하는 동일한 공개 lifecycle 진입점을 호출한다.
- 이 문제는 의존성의 lifecycle 분기와 픽셀 재현으로 원인이 좁혀진 코드 검토 결함이다. diagnosing-bugs의 추가 가설 3–5개와 임시 로그 단계는 이 근거로 생략했으며, 장시간 성능 진단 전체를 완료했다고 간주하지 않는다.
- WGC 미전송 상태 수정은 제어 흐름 근거와 네이티브 픽셀 시험으로 확인했다. 이 시험만으로 500ms 지연의 실기기 회귀 측정이 끝났다고 표시하지 않는다.
- 빈 캡처 풀은 정상 상태로 처리하고, 풀의 두 버퍼 중 최신만 CPU로 읽는다. Microsoft의 [TryGetNextFrame 계약](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.trygetnextframe?view=winrt-26100)은 빈 풀에서 null 반환을 명시한다. `capture_probe`에서 시작 전 빈 풀을 직접 검사했다.
- USB 인증은 페어링 코드를 요구하고, 다섯 번의 서로 다른 실패 후 60초 제한한다. USB 재연결로 제한이 초기화되지 않는 테스트도 실패 → 수정 → 통과했다. 기존 유효 토큰 인증은 유지한다.
- Swift 인코더와 Rust 수신기가 `proto/testdata/deskink-ink.json`을 공유하는 계약 테스트를 추가했다. 64비트 선 ID의 최댓값도 포함한다. Rust 쪽 실행과 Swift 쪽 미실행을 구분하며 이 추가 테스트를 red–green 완료로 집계하지 않는다.

이 작업은 첫 구현에 대한 결함 수정과 검토다. 계획 4단계의 전체 오류·보안·성능 진단 및 5단계의 전체 구조 개선은 실기기와 후속 기능을 포함해 계속 수행해야 한다.
